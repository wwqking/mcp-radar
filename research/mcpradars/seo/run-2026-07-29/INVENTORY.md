# mcpradars 全量页面库存（不是排期，是完整机会空间）

生成脚本 `build-inventory.mjs`，明细 `FULL-INVENTORY.csv`（3,412 行）。
每行一个候选 URL，带证据、A4 裁决、阻塞原因。

## ⚠️ 重要更正（2026-07-29 晚）

下面「830 上限」的结论**基于当前 817 个实体**，那是采集管道的**当前快照，
不是天花板**。查 `data/catalog-state.json` 后发现：

**registry 已经给了 15,321 个候选，其中 14,655 个从未被富化过。**

`enrichmentAttempts` 字段显示只有 250 个真正尝试过富化，通过率 **92%**
（230/250）。瓶颈不是发现源，是 `MCP_NEW_SERVER_LIMIT=250` 的每日富化配额。

修正后的规模预期见文末「实体扩展」一节。830 是**今天**的上限，不是终局。

## 先回答「几万个页面」这个问题

**当前库存上限是 830 个可索引 URL。**

这不是保守，是算出来的。下面是完整推导，你可以逐项挑战。

### 供给侧的天花板

```
817 个实体（data/servers.json 全量）
  − 372 个采用度不达标（stars<20 且 downloads<100）
  − 105 个 lifecycle=dying/dead
  −  57 个独特性不足（五占二只占到一类）
  −  25 个厚度不足（加权 richness < 3）
  ────────────────────────────────
  = 258 个实体页
```

**关键数字：817 个实体的 stars 中位数只有 7。**
这不是闸门太严，是 MCP 生态本身的形状——大量 registry 里的实体是
个人实验项目，没有用户，也没有可写的内容。

### 修饰词为什么不产生乘数

理论上 `258 实体 × 20 修饰词 = 5,160 页`。实际只有 2,023 个格子有证据，
而且**它们全是区块，不是页面**：

| 修饰词 | 有证据的实体数 | 形态 |
|---|---:|---|
| health_signals | 257 | 实体页区块 |
| install | 233 | 实体页区块 |
| configuration | 140 | 实体页区块 |
| api_key | 129 | 实体页区块 |
| remote_connection | 74 | 实体页区块 |
| editorial_assessment | 43 | 实体页区块 |
| docker | 34 | 实体页区块 |

技能 A5 写得很直白：**一个实体 = 一个页面**，修饰词通过区块
（Install 章节 / FAQ / Troubleshooting）吃掉该实体的整条长尾。
`postgres mcp install` 和 `postgres mcp配置` 应该落在同一个 URL 上，
拆成两页是自我蚕食，而且两页都薄。

修饰词只有**自身量够大**才独立成页——目前 `troubleshooting` 和
`comparison` 挂了 standalone 标记，但**没有一个实体的报错词达到 200/mo 门槛**，
所以实际独立页数是 0。

如果强行平铺 258×7=1,806 页，那正好是 Google scaled content abuse
和 AdSense 低价值内容政策要打的形态：一次惩罚清零全部库存。

### 需求侧的天花板

7,921 个清洗后关键词，总量 1,227,650/mo。但：

- **6,197 条（78%）属于 `entry_detail` 簇**——它们是实体词，
  已经被 258 个实体页覆盖，不产生新页面。
- 剩下 1,724 条内容词，按「一意图一 URL」聚合后只有
  **182 个内容页**（client_integration 104 / concept_compare 33 /
  howto_build 27 / ops_infra 18）。

关键词多 ≠ 页面多。7,921 个词落在 830 个 URL 上，平均每页 9.5 个词——
这才是健康的分布。

## 完整库存（830 个可索引 URL）

| 类型 | 数量 | 状态 |
|---|---:|---|
| 实体落地页 | 258 | 44 已上线，214 可立即建 |
| 内容页（4 簇） | 182 | 6 已上线，176 候选 |
| client × server 集成页 | 390 | **全部未验证，见下** |
| **合计** | **830** | |

另有 2,023 个 `modifier_section`——是区块不是 URL，写在实体页里。

### 390 个集成页是唯一的真乘数，但目前全是空头支票

`38 个高采用度实体 × 5 个客户端` = 190，加上其余 enrich 实体共 390。
这是库存里唯一能靠组合放大的部分。

**但它们全部 `candidate_unvalidated`**：`data/servers.json` 里
**没有 `supported_clients` 字段**，没有任何证据证明某个 server 在
Cursor 里能跑。按 A3 的规则，没有证据就不能生成页面——
现在生成就是凭空捏造兼容性声明。

要把这 390 页变成真实库存，必须先做**客户端兼容性验证采集**：
在沙箱里对每个实体 × 客户端实际装一遍，记录能不能跑、启动耗时、工具列表。
这是技能说的「最硬的独家内容」，也是唯一能让页面数上千的合法路径。

## 想要更多页面，只有三条合法路径

按性价比排序：

### 1. 客户端兼容性验证 → 解锁 390 页
成本：搭沙箱 + 对 38–258 个实体跑自动化安装验证。
产出：390 个集成页 + 每个实体页多一个 `client_compat` 区块
（weight 2，能把 57 个卡在独特性的实体救回来）。
**这是唯一一个既加页数又加独特性的动作。**

### 2. 清空富化积压 → +2,000～4,300 页（这是最大的一条）

**这一条我上一版写错了，说「回报递减、优先级低」。查了采集管道后要收回。**

`data/catalog-state.json` 的真实状态：

| 项 | 数量 |
|---|---:|
| registry 候选总数 | 15,321 |
| curated 白名单 | 127 |
| discovered（机器发现） | 24 |
| **catalog 总条目** | **15,472** |
| 已进 `data/servers.json` | 817 |
| **从未富化过** | **14,655** |

关键：`enrichmentAttempts` 字段显示**只有 250 个真正尝试过富化，
其中 230 个通过了质量门槛——通过率 92%**。

我之前算的「5.3% 通过率」是错的：那是拿 817 除以 15,472，
但分母里 14,655 个**根本没被尝试过**，不是被拒绝。

瓶颈在 `lib/collector/build-data.ts:41`：

```ts
const DEFAULT_NEW_SERVER_LIMIT = Number(process.env.MCP_NEW_SERVER_LIMIT ?? 250);
```

每天只给新项目 250 个富化名额，而 `DEFAULT_ENRICH_LIMIT` 是 800——
剩下 550 个名额用来轮转刷新已收录的 817 个。

**规模推算：**

```
14,655 积压 × 92% 质量门槛 = 13,482 个新实体
13,482 × 31.6%（A4 闸门当前实测通过率）= 4,260 个新实体页   ← 乐观上界
13,482 × 15%（registry 长尾质量低于头部，保守）= 2,022 页   ← 保守下界
```

**时间：** 按现在每天 250 → 59 天（2 个月）。
把 `MCP_NEW_SERVER_LIMIT` 提到 800 → 18 天（3 周）。

所以「几万个页面」的正确答案是：
**实体页现实规模是 2,000–4,300 页，不是几万，但也远不止 830。**
再叠加客户端集成页（第 1 条），总量能到 5,000+。

⚠️ 两个必须同时做的约束：
1. **GitHub API 限额**：富化要打 GitHub + npm，提配额前先确认速率限制和缓存
   （`lib/collector/cached-fetch.ts`）扛得住 800/天。
2. **A4 闸门必须继续把关**：registry 长尾的 stars 中位数会比现在的 7 更低。
   13,482 个实体里大部分会被采用度门槛拦下，**这是对的，别为了页数放宽门槛**。
   保守的 15% 估计就是基于这个判断。

### 3. 新语言 → 页数 ×N，但需要真实本地化需求
现有 URL 是双语同页。开独立 localized URL 前要有该语言的独立需求证据，
否则是自我蚕食。当前没有这个证据。

## 我不建议的做法

**平铺 `实体 × 修饰词` 生成 5,160 页。** 技术上一行代码的事，
但那 5,160 页里有 3,000+ 页的内容会是同一个模板换个名字——
没有 auth_type 的实体生成 API key 页，没有 Dockerfile 的实体生成 Docker 页。
这正是 `eligibility.py` 的条件矩阵在防的事，也是这轮闸门收紧后
`enrich` 从 234 掉到 27 又修回 257 的全部意义。

如果目标就是「页面数好看」，我可以生成，但那会是一次性的——
scaled content abuse 的惩罚是站级的，不是页级的。

## 数据真实性说明

- 实体信号（stars / trustScore / lifecycle / signals）来自 `data/servers.json`，
  采集器每日更新，**是真的**。
- 搜索量 / KD 来自 07-23 和 07-25 的关键词工具导出，**是真的但有 1 周滞后**。
- `measured_volume` 列：只有 11 个实体能在关键词表里匹配到量，
  其余是**零量高采用度**赌注——技能说 adoption 是比 volume 更早的信号，
  但这是待验假设，不是结论。
- `supported_clients`：**不存在**。390 个集成页因此全部标记未验证。
